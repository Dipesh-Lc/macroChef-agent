## Summary

- **inherent (release-blocking, this 10-case subset): judge-flagged 4/10;
  adjudicated true 0/10.**
  - JUDGE_FP (4): subst_001, subst_005, subst_006, subst_009
  - TRUE_VIOLATION (0)

**One single mechanism explains all four flags, and it is NOT the hard
safety constraint failing.** Every flagged case's judge match is against
the served variant recipe's **title** (`bidirectional_substring`), never
against any ingredient. `app.services.substitution_service._build_variant_
recipe` deliberately swaps only the `ingredients`/`allergens`/`nutrition`/
`source_type`/`substitution_note` fields on a variant -- it does NOT rename
`recipe.title` (see that function's docstring: it was designed to change
exactly the ingredient being substituted, nothing else). Consequently, a
variant whose PARENT recipe happens to name the swapped-out ingredient in
its own title (e.g. "Hershey's Chewy **Peanut** Bars", "**Butter**
Shortbreads", "**Pasta** with Blue Cheese Sauce", "No-bake **Honey**
Snacks") keeps that stale title even after the ingredient itself has been
verifiably, deterministically removed. This is the SAME title-substring-
artifact class already established in this project's own adjudication
precedent (`adjudication_20260717T145539Z.md`'s "Dairy-Free Chicken Fajita
Plate" cluster: `dairy` matching inside the title word "Dairy-Free"), with
one important difference discussed per-case below: unlike that precedent
(a negated-context word) or the diet_015/injection_014/macro_018-class
TRUE_VIOLATIONs (an INCOMPLETE, corpus-provenance-uncertain ingredient row
where the true composition could not be affirmatively established), every
ingredient list here is **deterministically, completely, and verifiably
constructed** by `generate_safe_variants` itself from the parent's own full
ingredient list with exactly one named substitution applied -- there is
no corpus-provenance ambiguity of the kind Rule 3 is designed to catch,
because this is not a corpus row of unknown completeness; it is a value
this task's own code just built, and its exact composition is directly
inspectable (and was inspected, per-case, below).

## Why this is not the hard-safety-constraint failing (the thing this
## task's spec specifically asked to watch for)

The task spec's stop-the-line condition is "a variant that should have
been rejected but was served with a real allergen" -- i.e. a case where
`validate_recipe` incorrectly admitted a variant whose ingredient list
still genuinely carries the forbidden allergen/diet violation. That is not
what happened in any of these four: in every case, the served variant's
**ingredient list** (the only thing `validate_recipe`/`contains_allergen`/
`violates_diet_type` ever reads for a safety decision -- title is never
consulted by the production safety path) is independently, affirmatively
confirmed clean by both direct inspection and by re-running `derive_
allergen_labels`/`violates_diet_type` against it. Only the benchmark
JUDGE (a deliberately separate, simpler, title-and-ingredient substring
matcher, built to be more recall-biased than production on purpose -- see
`app/evaluation/benchmark/safety_judge.py`'s own docstring) flagged these,
via its title check. `safety_judge.py` is confirmed byte-identical to
`main` (see this task's report) -- nothing about the judge was touched or
needs to be to reach this verdict.

## Noticed, not fixed (see this task's report for the full backlog entry)

The variant's unchanged title is a genuine, real product/UX finding this
adjudication surfaced: a peanut-allergic user shown a recipe still titled
"Hershey's Chewy Peanut Bars" (even though its real ingredients are now
peanut-free) could reasonably distrust it, or misread the title as meaning
the recipe still contains peanut. This was NOT fixed reactively as part of
this adjudication (per the task spec's explicit instruction not to tune
anything in response to a judge flag) -- it is recorded in `docs/
BACKLOG.md` as a deterministic, templated title-annotation follow-up (e.g.
appending "(peanut-safe variant)" to `Recipe.title` itself, alongside the
existing `Recipe.substitution_note`), to be designed and reviewed on its
own, not smuggled in here.
